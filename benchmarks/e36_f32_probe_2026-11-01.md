# Does f32 feature storage lose ladder signal on E36? (2026-11-01)

Question (owner): the scoring and training paths cast each raw revision-7 feature to f32 before use; if the scale of a
feature wastes f32 precision, a postprocessing step (complement, log, offset) could keep more signal.

Data: E36 rev7 features, run `e36-features-20261101` (extractor `ed495741`, zenmetrics `d46ec235` index `bfcae809`).
300 references drawn at random (seed 20261101) from 8,657 jobs: 28,854 views, 2,294 ladders (reference, codec,
mode_key), 26,560 adjacent-q rung pairs. Source values are the worker CSVs (f64, shortest round-trip decimals).

Script: `scripts/byconstruction/e36_f32_ladder_probe.py LEDGER CAS INDEX 300 COLS`. For each adjacent rung pair it
counts pairs whose f64 values differ but whose f32 casts are equal ("collapsed"), and on those asks whether the f64
order agrees with q (higher q, less loss) and with butteraugli_pnorm3.

`var_loss = max(0, 1 - var_dst/var_src)`: the collapsed values sit at 1 - 3e-8 (heavily degraded rungs whose
distorted variance is ~3e-8 of the reference's), with f64 gaps of ~1e-10. The v2 collapses sit at values ~1e-3 with
f64 gaps ~1e-13 (relative ~1e-10).

Finding: where f32 ties two rungs, the f64 order is a coin flip against both q and butteraugli. The digits f32 drops
are numerical noise, so no complement/log/offset postprocessing is warranted for storage. No two views of one
reference become identical across all 1,825 columns after the cast (0 of 29,465 views in a 300-file CSV pass).
Not tested: transforms for learning (feature conditioning), which is a trainer question, not a storage one.
